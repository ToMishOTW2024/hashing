Hashing Lab: from one array slot to web-scale similarity search

Hashing is not one algorithm. It is a family of ideas that trades exact structure for fast placement, compact fingerprints, stable distribution, or approximate similarity. This lab starts with a RAM array and ends with distributed systems and near-duplicate search.

1. Bottom up: what a hash is trying to buy

An array can retrieve item A[i] in constant time because the address is computed directly: base address + i × element-size. The hard part is that real keys are not compact array indexes: they are strings, user IDs, packets, files, objects, and vectors.

arbitrary key → hash function h(key) → integer fingerprint → table slot h(key) mod m

Exact lookup

“Find customer mishfaq@example.org exactly.” Hash tables, caches, compiler symbol tables, database indexes, and packet-flow maps commonly use this form.

Goal: equality

Similarity lookup

“Find documents that are nearly the same.” MinHash, SimHash, and LSH deliberately make similar inputs more likely to collide.

Goal: near neighbors

Stable placement

“Which server owns this key after the cluster changes?” Consistent-hashing families minimize movement rather than merely spreading keys.

Goal: minimal remapping
The word “collision” means two different inputs produce the same hash output. For a regular hash table, collisions are an inconvenience to resolve. For locality-sensitive hashing, collision is often the signal that two objects may be similar.

Why ordinary hashing is fast

With a well-distributed hash, expected bucket occupancy is the load factor \( \alpha = n/m \). In chaining, expected work is \(O(1+\alpha)\). Keeping \(\alpha\) bounded—often roughly below 0.7 to 0.9 depending on the design—keeps operations near constant time.

Why it can still be slow

Worst case is \(O(n)\): many keys can collide, a poor hash can cluster keys, or an attacker can choose adversarial inputs. Security-sensitive interfaces use keyed or randomized hashing so an adversary cannot cheaply precompute a collision flood.

3. Where “\(O(1)\)” really comes from

Hash-table \(O(1)\) is normally an expected and/or amortized statement. It relies on bounded load, a sufficiently random-looking hash, and the usual RAM-model assumption that machine-word operations are constant time.

Expected constant work

E[work] ≈ O(1 + α)

If the table stays at a bounded load factor, the expected number of collisions or probes stays bounded even as \(n\) grows. A universal hash family formalizes a useful promise: for distinct keys \(x,y\), the probability of collision under a random choice of hash function is at most about \(1/m\).

Amortized constant resizing

1 + 2 + 4 + ... + n < 2n

A resize is expensive because it allocates a larger array and reinserts all current entries. But when capacity doubles, an item survives many cheap insertions before it is moved again. Over \(n\) insertions, total copying remains \(O(n)\), making average cost per insertion \(O(1)\) amortized.

A hash table is not “better than a tree” in every task. If you need “all keys between 10,000 and 20,000,” sorted order matters, and a B-tree or balanced tree is the appropriate baseline.

4. Real hardware: the memory system often dominates

Modern CPUs can perform arithmetic very quickly, but a pointer chase that misses cache can cost far more than the hash calculation. This is why many production hash tables prefer contiguous arrays and small metadata bytes over linked lists scattered across memory.

CPU caches

Arrays pack related data into nearby cache lines. Open addressing can inspect nearby slots sequentially; pointer-heavy chaining may require fetching unrelated memory locations.

Locality matters

SIMD group scan

Swiss-table-style designs keep compact control bytes—such as empty/deleted state and a short hash tag—in a contiguous array. One SIMD instruction compares many tags at once; only candidate payloads need full key comparisons.

Many tags per instruction

Hash calculation

Non-cryptographic functions such as xxHash-family functions aim for speed and distribution. Keyed functions such as SipHash defend hash tables exposed to hostile keys. SIMD-oriented designs such as HighwayHash exploit vector multiply and permutation operations.

Speed vs adversaries

A realistic lookup path

  1. Compute a 64-bit hash of the key.
  2. Use some bits to choose a starting group or bucket.
  3. Use a short fingerprint/tag to reject most non-matches cheaply.
  4. Compare full keys only for matching tags.
  5. Probe another nearby group if necessary.

Hardware and networking examples

Hardware and software network stacks hash packet tuples such as source/destination IP, ports, and protocol to select a receive queue, connection state, or load-balancer backend. A production Google load-balancing design, Maglev, uses a precomputed lookup table to make the per-flow choice effectively one table access while preserving substantial assignment stability after backend failures or changes. [33][37]

Practical lesson: asymptotic notation predicts scaling, but it does not count cache misses, branch mispredictions, contention, or memory allocation. For a hot lookup path, those details frequently determine the winning hash-table design.

5. Similarity hashing: collisions on purpose

Standard hashing tries to make even tiny input changes look unrelated. Similarity hashing reverses that design: related objects should collide more often than unrelated ones. The result is approximate search, not proof of equality.

MinHash

First convert an object into a set, such as word or character shingles. Apply random-looking permutations/hashes and retain each minimum. The key identity is:

P[minhash(A) = minhash(B)] = Jaccard(A,B)

Thus the fraction of matching signature components estimates set overlap.

SimHash

Convert features into signed random projections, sum them, and keep only each sign bit. Similar weighted vectors tend to have a small Hamming distance. SimHash targets cosine-style similarity rather than Jaccard set resemblance.

LSH banding

Instead of comparing every pair among \(N\) documents—\(O(N^2)\) candidate pairs—split a MinHash signature into bands and index bands in hash tables. Only documents sharing a band become candidates for an exact verification step.

Example: plagiarism triage or web-page deduplication can first use shingle-based MinHash/LSH to find a tiny candidate set, then run a more exact and expensive comparison only on those candidates. That is usually much cheaper than comparing every document to every other document.

6. Consistent hashing: stable ownership when servers change

Suppose a cache cluster has \(N\) servers. A naïve placement rule is server = hash(key) mod N. It balances keys well, but changing \(N\) usually changes the answer for most keys. That means broad cache invalidation and heavy data migration.

Ring + virtual nodes

Hash both keys and servers onto a circular numeric range; a key belongs to the next server clockwise. A new physical server takes responsibility mainly for nearby key intervals. Multiple virtual positions per server improve balance because one random point per server can leave uneven arcs.

Alternatives and trade-offs

Jump Consistent Hash uses almost no storage and provides excellent balance when buckets are numbered sequentially; its original formulation is less suitable when arbitrary named nodes must disappear. Rendezvous/HRW chooses the server with the best score for each key; it is very simple and stable but basic lookup evaluates every server, \(O(N)\). [32][5]

7. Current practice and likely direction

Standard/randomized hashing

  • Fast in-memory maps increasingly use compact metadata, open addressing, and SIMD group scans rather than pointer-heavy chains.
  • Universal or sufficiently independent randomized families remain important for analysis and resistance to pathological key patterns.
  • Keyed hashes are essential at hostile boundaries, where input-controlled collision attacks can turn nominal \(O(1)\) behavior into a denial-of-service risk.
  • Cuckoo variants and bucketized designs offer bounded or very short lookup paths, especially appealing for read-heavy systems.
  • Hardware-aware design continues to favor fewer cache misses and more predictable branches, even when two choices share the same Big-O notation.

Similarity-based hashing

  • MinHash remains a practical baseline for Jaccard-style set similarity, with one-permutation and densification techniques reducing signature-generation cost. [17]
  • SimHash remains useful for inexpensive near-duplicate fingerprinting, especially where a compact Hamming-distance representation is desirable.
  • For dense neural embeddings, graph-based approximate-nearest-neighbor indexes often dominate operational semantic search; LSH remains valuable when its probabilistic guarantee matches the metric, streaming constraints, privacy approach, or distributed architecture.
  • Hybrid retrieval systems increasingly combine lexical signals, compact sketches, metadata filters, and embedding search rather than treating any single index as universal.
  • Privacy-preserving and federated similarity estimation are active directions, including MinHash-based approaches under local differential privacy. [20]
A useful design rule: first name the quantity you must preserve—exact equality, Jaccard overlap, cosine similarity, range order, stable server ownership, or cryptographic integrity. Then select a hash family and data layout. “Use hashing” is not yet a complete engineering decision.
